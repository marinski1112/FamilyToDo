# 長期利用のDB読み込み・データライフサイクル点検

点検日: 2026-10-07。コード・migration・合成SQLiteデータを対象。本番D1の手動操作、Observability、課金/設定変更、家族データの自動変更を行わない。本番容量・実クエリのrows_read/遅延は未計測で、長年無制限に問題ないという保証ではない。

## 今回の是正

|対象|問題|対応|
|---|---|---|
|料理履歴|LIMIT 50でもstatus除外と並べ替えで家族履歴全体を読む可能性|非ACTIVEの履歴順partial index。2万件の合成履歴で索引使用・全履歴のソート不要を確認|
|日誌・AIの直近調理|status/完了日で絞る索引が不一致|COOKEDのfamily/completed_at/id partial index|
|稼働queue・却下候補・未処理job|増えた履歴と混在して並べ替え|状態別partial indexと順序の一致|
|レシピ・URLの再試行検索|順序の同順位、動画同一区間のhash検索|active recipe順序とfamily/payload_hash/created_atの索引|
|候補読取り|新方式で紐づいているのに毎回レシピ200件を再読込してhash生成|旧形式の未紐づけIDがある場合だけlegacy照合。採用は候補IDの直接読取りで表示枠200件に依存しない|
|在庫|200件で切ると超過を検知せず一部の在庫で計算する可能性|201件目で超過検知・数量計算を停止。Web一覧は案内と整理導線。通常登録とレシートの200件上限は既にatomicで維持されているため、超過防止は既存/将来経路への防御|
|在庫一覧|期限のNULL順を含む並べ替え|familyと期限式・購入日・idの索引から201件まで取得してからrevisionと結合。外側の並べ替えは最大201行、revision/lotは同一SQLスナップショット|

migration 0017は索引追加のみ。既存データ・履歴・再送防止記録を削除/自動アーカイブしない。索引は保存容量と書込み処理を増やすため、将来の実測なしに無条件で追加し続けない。

## 現在の保持と長期課題

|データ|現行|評価・次の改善|
|---|---|---|
|レシピ・未採用の希望|永続、画面/提案は最新200件|長期に200件超の登録があると古いレシピを一覧・選択・AI候補から見つけにくい。Web/Android共通のカーソルページング・検索が必要。名前だけの重複削除はしない|
|採用/却下・queue|soft status、active100件、履歴/却下表示50件|古い履歴が消えたわけではないが、過去分の閲覧/復元ページングが必要。レシピsnapshotは元レシピ編集/非表示から調理内容を保護する|
|在庫|active200購入分、使い終わっても自動archiveしない|数量0の購入分も枠を使う。手動で一覧から外せる。0量を自動で外すときは、ある/なし管理や履歴を失わない条件と復元を先に設計する|
|在庫operations/events・買い物projection/job|再送防止・監査のため永続|安易な期限削除は古い送信の二重追加/二重消費/削除済み商品復活につながる。本文を圧縮する場合もfamily+ID+hash+確定結果の墓標と監査履歴を維持する|
|URL/動画取り込み・週間AI提案・レシート・離乳食AI下書き|結果/失敗をjob IDで永続保持、日次新規回数は有限|累積容量は有限ではない。20新規/日を10年使えば1種類で最大73,000 jobという計算になる（実利用の予測ではない）。未保存下書きの期限/書き出し、保存済み出典とreceipt item参照の分離、再試行の墓標が必要|
|公開検索・Liveセッション|新規処理時に7日超を家族単位/20件ずつ削除|Cronではなく処理時の整理。利用されない家族の行は残る。秘密の保存期限は個別制御。業務の再送防止記録を同じ方式で消さない|
|週間献立と旧調理記録|planはfamily/weekで更新、cooked_eventはplan_revisionを保持|旧版planの本文を保存していないため、後から週を編集すると旧調理版の料理名は復元できない場合がある。新しいqueueはsnapshot保持だが既存週間履歴は別。今後は完了時snapshot/版の履歴が必要。失われた過去内容をAIで補完しない|
|家族ログ・伝言・位置の共有DB|日時/家族/メンバー用の索引・位置日別archiveとscan cursorあり|この点検は献立と日誌投影が中心。共有DB全APIの大規模負荷・ファイル容量・退会時削除/エクスポートを完全検証した扱いにしない|

## 決定を必要とするライフサイクル案

1. 家族の記録・レシピ・完了履歴は原則保持し、閲覧をページングする。自動削除は導入しない。
2. 未保存のAI/URL下書きだけを期限付きにする場合、30日/90日などの期間と期限前の案内・保存/書き出しを決める。確定レシピの出典やレシートの反映記録を巻き込まない。
3. 再送防止の最小記録は残し、期限を過ぎた操作IDは再実行せず「期限切れ」とする。大きな結果JSONの圧縮/削除はこれを実装してから。
4. 在庫の0量整理は数量追跡lotだけを候補にして確認式にする。自動で家族データを変更する案は別途確認する。
5. 本番の現在容量・増加率・rows_read/writtenを、許可された運用手段で測ってから定期的な容量計画を作る。この点検では取得していない。

## 公式仕様と検証範囲

2026-10-07参照: [D1 Limits](https://developers.cloudflare.com/d1/platform/limits/)、[Use indexes](https://developers.cloudflare.com/d1/best-practices/use-indexes/)、[D1 Pricingのrows read/written定義](https://developers.cloudflare.com/d1/platform/pricing/)。D1は返却行数だけでなく走査行数を数える。索引も容量・書込みを使用する。容量・実行時間・クエリ回数のプラン別上限があり、契約プランの変更はしていない。Time Travelは短期復旧であり年単位の履歴保存の代替ではない。

合成検証: 2万件queueの索引/有限返却、表示枠外の候補ID採用/家族分離、不要legacyレシピ読取りなし、在庫201件で部分計算拒否と整理後の復帰。既存の200件上限・revision・atomic在庫・冪等買い物・Live/AI予算の回帰も実行。実認証は配色と画面表示の確認。家族データの実保存・実スマホ/Android認証QAは別。
