# 今回作るもの（買い物までの日付なし献立）

2026-10-07。日常の入口は「今回作るもの」。既存の週間献立は日付を決める場合に併用でき、既存データは自動移行・削除しない。

- 食べたいものは具体的な料理にも「魚（安いものがあれば）」にも対応する。レシピの登録は必須ではない。
- 採用 → 日付なしの今回作るものへ。保留は操作不要。却下 → 候補から外れ、最近50件の却下一覧から戻せる。レシピは消さない。
- レシピ付きの採用は材料・手順のスナップショットと人数を保存する。後の元レシピの編集・非表示で調理内容が変わらない。レシピなしの希望にも、後でレシピを紐づけられる。
- 未追加の料理から買うものをまとめて確認。数量・単位の集約と正確な在庫差引きは既存の決定論的計算。漠然とした希望は入力した名前をそのまま追加し、食材や数量をAIで推測しない。選択した食材だけ追加する。
- 追加確認は対象料理全体を1回分として扱う。選択しなかった食材・追加後に変更した人数やレシピの差分は既存の買い物画面で調整する。自動で追加済み商品を削除・再生成しない。
- 料理完了 → 一覧から外れ、最近50件の履歴に表示。正確な在庫は表示数量を明示確認した場合だけ減らす。レシピなしでも完了可、在庫量を推測しない。
- 未調理の料理は日付・買い物済みによって消えない。不要になれば「食べたいものに戻す」。追加済みの買い物は残す。

## データと再試行

MEALS_DB migration 0016（既存のGitHubデプロイ経由）。wishlist.status は PENDING / ADOPTED / REJECTED。採用と候補の非表示は同一transaction。queue は ACTIVE / COOKED / DROPPED、家族ごと100件まで。採用のrequest_idとpayload hash、編集revision、完了token・在庫revisionで二重処理と古い上書きを防ぐ。履歴を物理削除しない。一覧はレシピ要約のみ返し、材料・手順は個別の調理時に取得する。全レシピsnapshotを毎ページで転送しない。

買い物は既存DBの shopping_items が正本。MEALS_DBで有限の対象集合と選択済みproductsの不変jobを確保し、既存DBの meal_shopping_projections へ `cycle-<job id>` で冪等反映する。途中障害は PENDING job から同じ内容を再開。商品を人が削除した後の再試行で再生成しない。異なるjobが同じ料理を二重に確保しない。job確保後の料理変更や完了でも、再開内容は確認済み内容のまま。

採用済み・却下済みの希望に対する旧紐づけ操作は拒否。旧wishlist_deleteは候補のみ却下扱い。レシピとの追加opt-inで同じレシピの希望を無条件に再作成しない。名前だけで異なるレシピ・希望を統合しない。

## 調理・AI

レシピ付きの今回作るものも既存のWeb手順・人数換算・ローカルタイマー・Cooking Liveを使用。Liveは queue_id + revision で家族のACTIVEスナップショットを読み、任意クライアントrecipeを信用しない。既存の送信同意・セッション/予算/429縮退を維持。AI・マイク通信は本人の開始操作のみ。レシピなしの希望に調理手順を捏造しない。

Androidは同じ公開APIを使用。ネイティブで採用・候補・紐づけ・買い物・完了、Liveは外部ブラウザ。日付なし料理も既存の前景タイマーを使用する。

## 検証の区別

合成テスト: 日付/レシピなし採用、却下/復元、紐づけ後付け、レシピ非表示、連打/応答消失/再試行、競合、家族分離、買い物ブリッジ障害/再開/削除済み商品、明示在庫消費、Live正本コンテキスト。実認証・実機の確認結果はPR/引継ぎに別記する。本番の私的家族データを自動テストに使わない。
