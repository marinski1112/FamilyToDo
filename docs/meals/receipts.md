# レシートの読み取り・照合・在庫確認

「ごはん→レシート」で写真または1行1品の手入力から最大40品を取り込みます。最近30件を一覧表示。写真はブラウザで長辺1600px以下のJPEG・500KB以下へ縮小し、明示操作でGeminiへ送信。JPEG/PNG/WebPを受け付け、原画像・動画・外部URL取得・R2/Files API保存は行いません。LINEからの受信手順は下記を参照してください。

## 確認の境界

読み取るのは購入商品ラベル、印字された整数の購入個数（不明はnull）、AI読み取り確度のみ。金額を数量にせず、g等への換算やレシピ食材への推測変換はしません。店舗/住所/氏名/カード等を出力しないよう指示し、出力schemaの追加フィールドや不正な個数を拒否。OCRの品目判定・確度そのものはAIの推定で、元レシートとの利用者照合が必要です。

元DBの自家族のpending/FAMILY買い物から最大200件を読み、NFKC/大小文字/空白の差を除いた同名だけ照合候補として表示。別家族・自分専用・完了済み項目は対象外。候補を選んで必要数量の購入を明示確認すると、この画面から購入済みにできます（下記参照）。自動完了・印字個数と必要数量の換算照合は行いません。

品目ごとの「数量を確認して在庫へ」で材料名・数量・単位・管理方法・購入日・期限・保存場所を編集します。数量管理を選ぶ場合、数量と単位は空欄から利用者が補います。印字個数で在庫を確定せず、保存するまで在庫は変更しません。receipt confirmation・inventory lot・ADD監査イベントを同一MEALS_DB transactionで原子的に保存。一意なlot IDと確定hashで並行保存・応答喪失再送も1lot、後から在庫を外した後の再送も復活しません。登録済み品目の訂正は在庫画面で行います。

## AI・保存・制限

MEAL_RECEIPT_PARSEの既存feature/audience routeを使用。既定は3.5 Flash-Lite→3.5 Flash、設定から変更可能。実際のプロジェクトでのモデル利用可否は検査用stubからは確認できません。全呼出しは既存project/model日budget・family/feature日budgetと429 circuitを予約後に実行。429/4xx、通信例外、不正出力では別モデル連鎖や修復呼出しを行わず、5xxだけ最大2モデル。未設定/上限/読み取り失敗時は手入力が使えます。

0006にreceipt_imports/itemsを追加。家族別request ID/payload hashによるclaimで同じジョブの並行生成を防止し、成功/失敗結果の再利用で再送時の余分な生成を防ぎます。新規は家族/UTC日20件（手入力も含む）。RUNNING途中中断の自動再生成はせず手入力を案内。保存するのはhash、処理状態、検証済み商品候補、確認済み在庫のドメインデータのみ。原画像、prompt、provider response本文、キーは保存/ログ出力せず、履歴は当面保持。商品ラベルに読み取り誤りが含まれる可能性は残るため確認画面を必須とします。

HTTP入力の上限拡張はreceipt_importのみ（JSON750KB、画像500KB、stream800KBで打ち切り）。他の献立操作は従来の150KB上限を維持。receipt 40品と買い物の最大100品をjson_eachで各1SQLにまとめ、無料D1のstatement budget内で一括保存。既存買い物ledgerと操作tokenによる冪等/削除後再送防止を維持。新Cron/identity複製/外部設定変更なし。

## 検証

献立41件SQLite/API/DOM、型・JS構文・静的参照、既存143件active regressionを確認。photo MIME/サイズ/権限、budget/circuit/429停止、5xx最大2回、schema拒否、画像・raw response非保存、家族/共有買い物分離、確認前未変更、監査失敗時rollback、並行保存/除外後再送、手入力縮退、日上限、40品/60買い物のstatement budgetを含みます。Chromiumでsynthetic画像の縮小→stub読取り→共有買い物照合→数量補完→在庫保存、両通信の応答喪失からの再試行、320/390/768px overflowなしを確認。実AI呼出し/実レシート/本番家族データは検査に使用していません。

## LINE写真の受信（0010）

個別トークで「レシート」を送信すると、そのメンバーの次の10分以内のLINE写真1枚を受け付けます。
受付返信で家族共有・Webでの読み取り開始を案内します。署名、active member、個別トーク、LINE contentProvider、イベント時刻を検証し、通常写真・外部URL・グループ写真は取り込みません。
受信と受付枠消費はMEALS_DBの同一batchです。command/event hashで再配送・古いコマンドによる再受付・写真の二重登録を防ぎ、家族/UTC日20件までです。

画像はWebhookでは取得しません。Web受信箱の「写真を確認」を押すと、ログイン・CSRF・家族所有を検証した固定LINE content endpointから取得します。
LINE message IDは専用purposeのAPP_SECRET派生AES-GCMで暗号化し、family/item IDをAADに含めます。キー・原message ID・cipherはWebやログに出しません。既存Secretsを使い、変更しません。
取得は1リクエスト・10秒・4MiB以下、redirect禁止、JPEG/PNG/WebPのMIME/マジックバイトを確認し、stream中でも上限超過で停止します。
ブラウザで既存の1600px/500KBのJPEGに縮小して確認表示し、Google Geminiへの送信を明示確認してから既存receipt_importへ渡します。
画像bytesはメモリのみで、D1/R2/Files API/localStorageには保存しません。取得の段階ではAIも在庫変更も行いません。

LINE取得の有効期限は受信後24時間です。読取成功・受信箱からの除外で取得cipherを消去し、期限経過分は次のLINE受信/受信箱参照/取得操作時に消去します。
定刻での物理消去を保証するCronは追加しません。期限後は取得できず、LINE側の保存期限等で24時間より早く取得不能になる場合もWeb写真選択/手入力が使えます。
取り込みjob IDは受信item IDを再利用します。応答喪失後に再び写真確認すると、完了済みの品目を表示し、画像再取得・AI再生成をしません。
確認済み/除外済み/期限切れのイベントhash行は再配送防止のため残します。原写真を保存しないため、後日原画像を参照する機能はありません。

LINE公式仕様: https://developers.line.biz/en/reference/messaging-api/#get-content

## レシートから買い物へ購入済みを反映（0117）

品目の同名共有買い物候補から1件を選択し、「必要な数量を購入した」ことをチェックして購入済みにします。
候補は自家族のpending/FAMILYのみで、NFKC・大小文字・空白を除いて同名のものに限定します。
候補・確認チェックの初期選択はありません。印字個数から必要数量を満たしたとは判断せず、在庫登録とも独立した明示操作です。
1つのレシート品目から反映できる買い物は1件です。同名の複数買い物を自動で一括完了しません。

serverは元の取り込みがREADY/errorなしであること、品目所有、label照合、選択した商品名/数量/updated_atのsnapshot、共有範囲・pendingを確認します。
反映は元DB内の単一batchで、operation receiptのclaim、shopping_itemsのcompleted/completed_by/completed_at、既存shopping_completion_historyのCOMPLETEDを同時に保存します。
既存買い物APIと同じ完了状態・履歴を使用し、AIや在庫更新は呼びません。
元DBの0117は二重適用防止用の小さな操作記録だけで、商品リストやレシート写真を複製しません。MEALS_DBへの書き戻しは不要で、品目表示時に操作記録を参照します。

同じ品目の並行確認・応答喪失再送でも履歴は1件です。後から買い物を未完了へ戻した・名前/数量を編集した・削除した場合も再送で上書きや復活をしません。
履歴画面の反映済み表示は、そのレシートからの操作を記録済みという意味であり、後日の買い物の状態を固定するものではありません。
確認後の買い物の訂正は既存買い物画面で操作します。異なる候補へ同じ品目を再反映せず、他候補が必要な場合も既存買い物画面を使用してください。
