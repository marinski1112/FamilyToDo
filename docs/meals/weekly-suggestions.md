# 週間献立の提案

今週の献立から「今週の5品を提案」を開き、人数・1品の調理時間上限を選びます。提案→確認→編集欄へ反映→下書き保存/献立確定の順です。提案だけではweekly_plans、shopping_items、在庫を変更しません。土日の献立と未保存の編集は保持します。保存は既存の楽観revision確認を通ります。

## 候補とAIの役割

自分の家族のactiveレシピを最大200件読み、時間内の候補を通常コードでスコアリング。料理名と食べたいものの文字一致に加点し、過去30日間の作った記録に現存する献立snapshotを照合して減点します。調理時間にも軽い重みを付け、上位30件に限定します。アーカイブレシピ、別家族のレシピ、時間上限外の料理は候補に入れません。

Geminiへは候補ID・料理名・調理時間・wish/recentフラグ・scoreのみ送信します。材料/手順、出典URL、家族やメンバーのプロフィール、カレンダー等は送信しません。AIは候補IDを5件選ぶだけです。日付と人数は通常コードで付けます。厳密なJSON形状・候補の存在・必要な種類数を検証し、候補外ID、数量や説明の追加、壊れた回答は採用しません。

MEAL_WEEKLY_PLANルートを家族・メンバー区分から解決し、既存のgeminiFetch共通予算・429 circuit・安全な呼出し集計を通します。通常1回、5xxだけ代替モデルに最大1回。429、4xx、無効JSON、回答修復目的の再呼出しはありません。未設定/別provider/上限/障害/不正出力は通常コードの順位から5件を選んで表示します。候補1件ならAIを呼びません。候補が5件未満の時は全候補を使ってから繰り返し、画面に明示します。

アレルギー、離乳食安全判定、在庫スコア、栄養判定、未登録レシピの生成は今回の提案に含めません。料理の安全性を保証する表示は行いません。

## 再送とデータ

MEALS_DBの0003 migrationを追加します。family_id/request_idを原子的にclaimし、同じ条件の再送では保存済みの提案を返します。並行要求は先行処理中のため拒否し、追加provider呼出しを行いません。保存に失敗してRUNNINGが残った場合も自動再生成しません。利用者は戻って新しい提案を作成できます。

1家族1日（UTC）20件の新規提案まで、AI未使用も含みます。同じIDの再送は件数を増やしません。IDを別条件で再利用した場合は拒否します。クライアントは条件が同じ通信失敗時に同一IDを再利用します。本文・raw model response・promptはログ/AI台帳へ保存しません。提案履歴にはサーバで再構成した料理ID・料理名・所要時間と入力条件のhashを保持します。重複排除の履歴は現段階で自動削除しません。
