# 主菜チェックと複数の副菜

レシピと食べたいものに `is_main` を保存する。チェックありは主菜、なしは副菜・汁物・お菓子など。名前やAIだけで分類を確定しない。migration 0018の既存データはチェックなしで、過去の献立内容は変更しない。既存の主菜レシピは編集画面からチェックできる。

URL/YouTube取り込み時に指定し、確認フォームで変更してから保存する。レシピと希望を同時追加/明示紐づけすると、確認フォームのチェックも希望へ反映する。希望一覧でのチェック変更は希望側だけに適用し、元レシピを書き換えない。旧Android等のレシピ編集で項目が省略された場合は既存の値を維持する。新規希望は省略時false。希望の変更は家族・PENDING・revisionで制限し、採用時の分類をqueueへ固定保存する。採用後の元レシピ変更は採用済み分類を変更しない。

週間主菜提案はチェック済みの登録レシピだけを対象にする。外部候補は未確定のまま確認フォームで主菜/副菜を確認して保存する。候補がない場合、レシピで主菜をチェックする案内を出し、非主菜を勝手に選ばない。日付別の手動献立は主菜・中心の料理を1品、副菜などを0〜10品選べる。新しく選ぶ中心の料理は主菜チェックあり、副菜などはチェックなしだけを表示する。分類変更前/旧版で選択済みの料理は該当する欄に「選択済み・分類変更」として残し、読み込みだけで消さない。他の日や新規副菜欄の候補には含めない。主菜候補がないときはレシピ編集でチェックする。副菜のみ選び中心が未定のときは保存せず案内する。副菜欄は追加/削除できる。主菜と同じID、副菜内の同じID、別家族、非表示/不存在レシピ、新規10品超は拒否する。

複数副菜は従来のsides配列を使い、スナップショットと人数換算・買い物・在庫・調理手順へ全品を渡す。AI副菜提案は選択済みの副菜を置換せず追加し、10品超の場合は適用前に案内する。保存失敗時は全ての選択を保持する。旧1品保存APIとも互換。旧APKで新しい複数品献立を編集すると旧UIの1品だけに減るため、編集には対応APKを使用する（表示/調理は旧版もsidesを列挙する）。

実家族データの分類/保存を自動テストで変更しない。Web実認証QAは表示・未保存編集・取り込み指定を確認し、保存・計算・競合は合成DBで検証。Android API30/35は合成fixtureによるCI検証で実認証・実端末の代替にしない。
