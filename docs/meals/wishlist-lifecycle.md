# 食べたいもの・レシピの紐づけとライフサイクル

## 実装

- 希望は食べたい料理の意思、レシピは材料・手順。独立したIDを持ち、希望の `recipe_id` は同じ家族のレシピを参照する。
- 登録済みなら希望一覧に「登録済みレシピをひらく」。希望の元URLに登録済み候補がある場合も、新規取り込みを促さず既存レシピの選択を案内する。同じURLに複数の料理・動画区間があるため、URL・名前だけの自動紐づけはしない。
- 希望一覧で後付け・変更・解除。紐づけの更新番号を比較し、明示解除後に古い保存が紐づけを復活させない。競合や別家族・非表示のレシピへの新規紐づけを拒否する。解除しても両データは残る。
- 希望から取り込んだレシピを保存すると、元の希望に同一transactionで紐づける。新しい希望は作らない。紐づけ先が先に変更/削除されたら保存を拒否し、無関係なレシピを作らない。
- レシピ保存時の同時追加では既存希望を選択できる。既にそのレシピに紐づく希望がある場合は新規追加しない。同名だけの別希望には干渉しない。
- #1191のレシピ由来の希望IDは料理IDのhashと厳密に一致するため、表示時に既存レシピを認識する。推測による一括更新はしない。`recipe_link_set` は後から明示的に解除されたものを再推測で繋がないために使う。
- レシピ名を変更しても希望の名前・元URLは保存時の意思として残す。リンクを開けば最新のレシピが見える。非表示レシピの希望も残し、非表示であると示す。
- 希望の削除は希望だけ。レシピ、確定献立のsnapshot、調理済み履歴、在庫には波及しない。削除前の画面確認を追加した。既存削除APIは物理削除で、復元/ごみ箱は今回未実装。

スキーマ追加は `0014_meal_wish_recipe_links.sql` と `0015_meal_wish_link_revision.sql`。GitHubの既存deployがWorker更新前に適用する。手動で本番D1を更新しない。Androidの既存APIには追加フィールドだけで互換性を保つ。ネイティブの紐づけUIは未移植。

## 次の改善案（判断待ち、既存データは削除しない）

|対象|推奨する運用|
|---|---|
|重複した希望|同じrecipe_idを持つ候補を並べて、本人が残す希望を選択して統合。投稿者・元文・出典は統合元履歴へ残す。同名だけは候補表示まで。|
|重複したレシピ|URL・動画区間・材料・手順を比較し、本人が正本を選ぶ。希望の参照を移し、重複側は非表示。献立/調理済みsnapshotは書き換えない。完全削除は別操作。|
|希望のごみ箱|削除後30日など期限内の復元を用意する。保持期限は本人判断。削除前の再送が復活させないよう、最小限の再送抑止情報を本文から分離する。|
|希望を満たした後|調理済み・献立採用を理由に自動削除しない。『食べた/今回は見送る』で終了・再希望を明示する設計を推奨。|
|取り込みjob・LINE受信|確認/破棄後の本文保持期限と再送抑止情報の保持期限を分離。重複排除IDを無条件に消して再配信で復活させない。Cronの追加や変更はこの作業で行わない。|

注意: 現行のレシピ由来の固定希望IDは、削除後の同じIDでの再追加/再試行を区別できない。ごみ箱と再希望を実装する際に、保存操作IDとtombstoneを導入して整合させる。現段階で『全経路で重複・復活を完全に解消』とはしない。

## 検証

合成DB/DOMで家族分離、既存希望へのatomic保存、競合、解除、非表示、旧ID認識、明示解除後の再推測防止、同じ保存の再送、紐づけ応答消失時の選択保持を確認する。実家族データの統合・削除を検証目的で行わない。実LINE内の遷移とネイティブAndroidの紐づけは別検証。
