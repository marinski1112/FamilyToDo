## Data/state boundaries

Current notification functionality is intentionally split across different state families rather than one generic notification table:

- `notifications`: scheduled task/message/other operational reminders delivered by the Web Push notification worker.
- `web_push_subscriptions`: member/family-scoped browser Push subscription and delivery-health state.
- member notification fields: opt-in/channel selection used by notification settings and delivery eligibility.
- `line_daily_digest_settings`, `line_daily_digest_recipients`, `line_daily_digest_subject_settings`: family morning-digest configuration and eligible recipients/subjects.
- `line_daily_digest_receipts`: per-member/per-local-date LINE delivery receipt and retry state.
- daily digest AI guard/finalized-frame state: separate from LINE delivery receipts; generation success is not delivery success.
- `line_periodic_digest_receipts`: per-member/report-period weekly/monthly LINE delivery receipt and retry state.
- `line_periodic_digest_ai_reports`: weekly/monthly AI guard/finalized-frame state; separate from periodic delivery receipts.

Do not replace these with a single "notification settings" owner merely because they all affect messaging. Configuration, generation, delivery, transport, receipt/idempotency, and lifecycle repair have different invariants.

## Morning digest AI diagnostics boundary

The current settings page exposes a bounded generation-status view from the daily/periodic finalized generation state: generation status/reason, model where recorded, request count, period key and update time. The page explicitly treats that as **AI generation status, not evidence that LINE delivery succeeded**.

The daily generator stores bounded generation metadata in the finalized morning frame and can fall back deterministically when Gemini is disabled, unavailable, rate-limited, unsafe/invalid, or otherwise unusable. The deterministic fallback is part of the ACTIVE delivery contract; it must not be interpreted as proof that the scheduled job itself failed.

Do not document desired diagnostic fields such as `failure_stage`, `failure_reason`, or a specific `MORNING_DIGEST` diagnostic schema as implemented unless the current source/schema actually persists those exact fields. Product requirements are not implementation evidence.

Privacy rule: generation diagnostics must not become a storage path for prompt bodies, Gemini response bodies, profile bodies, Family Log bodies, raw location coordinates, Push credentials, LINE access tokens, or VAPID private material.

## Cleanup rules

- Do not merge `settingsNotifications()` and `webPushApi()`. The settings page owns member/family configuration; the API owns browser subscription lifecycle/test actions.
- Do not move VAPID/encryption code into `processNotifications()`. `webpush.ts` is the transport/crypto boundary; `notification-delivery.ts` is the due-work and notification-state owner.
- Do not treat the five-minute delivery scheduler as lifecycle repair. Send-time eligibility checks remain in `processNotifications()`; broader repair/audit work has deliberately lower-frequency owners.
- Do not infer that `members.notification_channel='LINE'` makes `notifications` rows a LINE-delivery queue. Current `processNotifications()` is a Web Push worker, while LINE daily/periodic digests have separate configuration, receipts and transport orchestration.
- Do not collapse daily digest AI generation state into `line_daily_digest_receipts`. A finalized AI/fallback frame can exist independently of whether LINE delivery later succeeds.
- Do not collapse weekly/monthly receipts into daily receipts. Their idempotency key is report type + period key, not local date alone.
- Do not bypass `line.ts#pushLineMessage()` with a second digest-specific HTTP transport. Digest owners select facts/destinations and own receipts; LINE transport sends the already-bounded message.
- Preserve deterministic fallback. AI failure/disablement/rate limiting must not make the morning or periodic summary depend on successful Gemini output.
- Keep generated prose subordinate to authoritative facts. Current digest code rejects unsafe/leaky output and numeric claims from generated narrative; factual counts/schedules remain server-rendered from canonical data.
- Do not log/store raw Push subscription secrets (`p256dh`, `auth`), endpoint values, VAPID private key/JWT, LINE tokens, prompt bodies, raw Gemini responses, private profile notes, Family Log body text, or raw GPS as diagnostic payloads.
- No notification owner or alias was classified DEAD in this pass. Search misses are supplemental evidence only; dynamic route/scheduled/external compatibility must be proven before deletion.
